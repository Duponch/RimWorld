# V259 — retirer la préparation répétée sans déplacer son coût

Le [prototype](../development/resident-render-preparation-v259.md) est physiquement exact dans sa fixture mais [écarté au coût complet](../history/validation-resident-render-preparation-v259.md). Produit V242/schéma 198 inchangés ; aucun gain FPS.

Les sources primaires relues sont la [documentation NodeMaterialObserver](https://threejs.org/docs/pages/NodeMaterialObserver.html) et celle des [UniformNode et groupes partagés](https://threejs.org/docs/pages/UniformNode.html), consultées le 8 octobre 2026. Le fonctionnement précis dépend du build local Three **0.186.0**, gelé avant/après chaque contrôle ; la documentation courante ne remplace pas cette référence.

Dans ce build, Renderer conserve updateForRender et les bindings partagés sur SHARED. FULL visite aussi les chemins d'objet, géométrie et bindings. Le monitor natif vérifie état du matériau, matrice, géométrie, lumière et textures ; supprimer son hasNode sans remplacer les dépendances donnerait un faux invariant. Un groupe partagé actualise au rendu, pas arbitrairement une fois par RAF : le vent peut changer entre deux dessins au même frameId. Les ombres et overrides demandent également les valeurs du matériau source.

La reconnaissance compilée a révélé plusieurs pièges concrets. DFG_LUT n'est pas une texture de scène ; camera Fn.once peut résider dans un cache de sortie transparent ; le matériau de référence map d'une ombre précède son override. ShaderCallNodeInternal ne rejoint pas toujours la liste plate builder.nodes : les événements d'instancing se trouvent dans les StackNode déjà compilés. InspectorNode peut avoir une fonction setup dormante native. Admettre une classe entière ou exécuter une Fn pour l'identifier ne serait pas équivalent. Les reprises reconnaissent seulement les identités et sorties existantes, avec bornes et refus conservateurs.

Le physique initial avait atteint quarante images avant un débordement de sérialisation du rapport. Son audit limité a surtout démontré zéro SHARED dans le grand corpus, donc l'absence de preuve du raccourci. La reprise native qualifiée compte bien 341 SHARED avant les cas négatifs et teste le refus avant mutation d'un matériau non configuré. Le rapport compact conserve les gros sidecars entiers ; ses assertions continuent à consommer les graphes complets.

Le coût ABBA établit une régression CPU de 22,03 %, malgré 12 792 SHARED par cohorte B. Le nombre de raccourcis ne mesure pas leur rentabilité. Le code conserve native.equals, capture des dépendances, comparaison et une seconde capture au commit après FULL. Ces parcours sont une cause plausible de surcharge, **pas une attribution chronométrée acquise** ; ni les compteurs ni la différence A/B ne donnent leur coût individuel. Le circuit inclut une queue GPU sérialisée et ne prédit pas des FPS.

La suite doit changer cette structure, sans retirer aveuglément ses gardes : établir non-échappement, writers et callbacks des objets réellement construits, puis dirty explicite partagé aux pipelines, avec APIs publiques/custom en FULL historique. Les graphes de rendu aujourd'hui accessibles ne deviennent pas propriétaires par un bool ou leur lieu de création. Le vrai Core ajoute ACES/exposure, Hemisphere, nuages, préparation/restauration et perte GPU, absents de cette première fixture. Aucun complément ni banc de ces domaines n'est engagé pour le candidat rejeté.
