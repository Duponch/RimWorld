# V260 — remplacer une recapture par un contrat de mutation

Le [prototype privé](../development/owned-render-preparation-v260.md) passe son premier [écran physique et coût complet](../history/validation-owned-render-preparation-v260.md). Le produit V242 reste inchangé. La baisse moyenne de CPU isolé motive la qualification suivante ; dispersion, froid et limites interdisent d'en déduire des FPS du jeu.

Les références primaires restent la [documentation NodeMaterialObserver](https://threejs.org/docs/pages/NodeMaterialObserver.html) et celle des [UniformNode](https://threejs.org/docs/pages/UniformNode.html), consultées le 8 octobre 2026, ainsi que le build local épinglé Three 0.186.0. Dans Renderer.js, SHARED conserve updateBefore, updateForRender, bindings partagés et updateAfter ; FULL visite aussi les géométries et bindings d'objet. Fréquence d'un callback et fréquence du groupe UBO sont distinctes. Aucun uniform OBJECT vivant ne peut être exempté parce que sa famille semble statique.

V259 était physiquement exact mais plus lent. Les recaptures constatées dans son code n'avaient pas d'attribution individuelle. V260 change le contrat : une construction privée garde les objets et leurs writers ; les mutations révoquent un ticket avant écriture et le succès externe acquitte seulement sa génération. Le premier contrôle gagne en moyenne malgré ses variations, ce qui ne prouve ni la part temporelle de chaque retrait ni la rentabilité du raccord réel.

Une façade ne suffit pas seule : TypeScript private/protected n'est pas une frontière runtime, un callback normal peut recevoir Core dans this, une Promise ou erreur peut rendre une référence. La fondation traite ces sorties avec captures d'entrées, petits DTO et receivers explicites, mais ses douze ports simulés ne qualifient pas le vrai renderer. Les prototypes interposés restent hors du domaine canonique déclaré ; cette fermeture n'est pas une isolation de JavaScript arbitraire.

La fixture couvre les pièges concrets : texture.dispose conserve sa version publique, une capacité remplace les buffers, Instance.beforeFrame dérive des attributs, un callback inconnu peut changer un autre matériau et une exception ne vaut pas un rendu réussi. Les pixels matériels complètent l'oracle CPU ; versions et compteurs ne certifient pas les uploads physiques. Une nouvelle cible n'est pas un nouveau GPUDevice.

Le vrai Core présente d'autres contraintes. Le singleton canonique toneMappingExposure est un RendererReferenceNode avec callback OBJECT et groupe RENDER ; l'audit actuel ne le reconnaît pas. Resource.presentChop écrit positions/normales/ranges à chaque pose utile, l'atlas terrain reçoit des copies GPU sans changement de version de destination, les assets et preparePresentationResources mutent aussi après await. Une invalidation globale à chaque RAF détruirait le bénéfice : retenir d'abord un périmètre statique fermé ou des dépendances locales réellement notifiées, tout en gardant les autres objets FULL et l'audit global des callbacks. Aucun second banc inchangé, nouvelle autorité raw, shader simplifié, règle ou cadence réduite n'est justifié.
