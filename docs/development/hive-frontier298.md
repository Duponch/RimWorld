# Ruches : effets du lot au front physique confirmé

31 octobre2026, schéma298 inchangé. Une nouvelle partie contenant des ruches pouvait arrêter la simulation avec « Actual Hive runtime refused: Invalid actual Hive Slime substep ». Le défaut concerne aussi la famille297.

Le traitement des ruches rejoue dix pas au macro, tandis que le propriétaire physique du dépôt exige l’instant réellement confirmé. Le lot transmettait un pas intermédiaire périmé. Le dépôt périodique et les dix dépôts lors de la naissance d’une ruche enfant présentent la même contradiction. Les mémos de retrait naturel pouvaient également être silencieusement refusés par la garde équivalente du Lord.

Ces trois appels utilisent désormais le front physique confirmé dans297/298. Les gardes Slime/Lord restent strictes. Les horloges internes et de naissance des ruches, l’ordre des opérations, les identités, les tirages RNG et la permutation partagée restent inchangés. Les schémas256–296 gardent leurs anciens arguments. Aucun champ sauvegardé ou migration n’est ajouté ; la cadence de ce sous-système reste au macro, sans nouvelle parité60Hz revendiquée.

Trois contrats de composant reproduisent deux échecs avant correction, avec le message exact signalé, puis passent tous après correction. Ils couvrent le plan non mutant avant commit, le refus d’un second commit, la conservation RNG/GenAdj/identités entre296/297/298 hors seuls timestamps de dépôt, la naissance intérieure conservée et le rejet strict d’un ancien sous-pas avant tout effet. Les fixtures partielles sont déclarées comme telles : elles ne prouvent pas une campagne jouée, un RAW complet ou un nouveau parcours Native. Le reçu positif de retrait Lord est porté littéralement ; aucun nouveau parcours positif de ce retrait n’est revendiqué.

Les [capsules initiales](starting-pod-frontier298.md) ont le correctif de frontière correspondant et leur propre preuve sur un vrai monde250×250 sauvegardé/rechargé. Aucun travail par image n’est ajouté aux ruches : seules les rares émissions d’effets lisent un timestamp scalaire. Aucun gain FPS ou coût CPU nul n’est déduit de ces contrôles. Les campagnes personnelles et de référence sont préservées.
